# 客户端改造与首批采集说明（供用户审核，未向客户端任务发送）

复用原有 HIL 录制、三路视频、14D state/action、RTC 队列、急停和现有控制限位。**不需要新增人工逐次按成功/失败键，不需要为了训练刻意高速接管。** 增加下面的 PLD 模式与执行记录即可；任务分类和奖励回填在服务端离线完成。

## 1. 先补齐两个部署事实

请客户端提供当前实际使用的 14D 目标下限/上限、每 tick 最大目标变化及其单位/来源；如夹爪有额外映射，必须给出映射，先统一到现有 Pi 物理目标语义。Thor 启动时读取实际 base 权重 SHA；不凭“20w”名字猜测现场服务身份。

物理配方提案：每臂 6 关节半径各 **±0.01 rad**，夹爪半径 **±0.02**；初始高斯标准差 0.2，作用在 tanh 前，通常远小于硬边界。边界还会随实际限位/连续性余量缩小。它不是末端固定下降 1 cm，也不承诺第一次就有提高。限位/最大步幅留空是因为必须取实际控制合同，不编造硬件参数。按 `configs/pld_rl/sac-contract-v1.template.json` 填好并审核，生成新版本，不能边采边改。

## 2. 增加四种实验模式与固定身份

- `probe`：完全执行 Pi，但记录同样的 PLD 状态/动作块/回执，作为同合同零修正基线。
- `collect`：执行当前 actor 的有界随机修正，用来学习；不要当成评估。
- `eval`：关闭采样噪声，执行 actor 均值；与 probe 做真机 A/B。
- `off`：原推理。可选 `shadow`：只计算 proposal，执行 Pi，仅用于联调，不作为带修正经验。

启动后握手核对 `pld.schema/contract_sha256/snapshot_sha256`。每轮固定 checkpoint/norm/engine、actor bundle、动作边界、任务文字；新 actor 只在一轮结束后热切换/重启加载，不在一次抓取内变化。

## 3. 抓取窗口与左右臂

用已有客户端状态/FK与 **当前已返回的 Pi 计划** 做因果进入：某臂在未来约 1 秒的计划中将由张开转闭合，且当前仍处于接近/下降，开启一次 attempt。闭合阈值/滞回沿用已核验的夹爪语义，不通过后验成功画面决定是否进入；窗口不要等到实际已经闭爪才开始。初期把触发时刻画回录像抽检，验证覆盖接近、下降。若无法稳定提前预测，先固定选择从每次 Pi 抓取接近动作开始，记录触发依据，不能拿离线切段时间当在线触发器。

左右臂都可触发；重叠时按最早计划闭合选一臂、同时时固定优先顺序。另一臂保持 Pi，记录此次未被修正。活动臂一次 attempt 内不切换。

以实际闭爪时 FK 高度为抬升参考。抬升至少 5 cm 且仍闭合时，继续记录多个新鲜画面，在**当前动作块结束**交还 Pi；无需停住 1 秒。资格窗口需能看清夹指中是否持物。发生早开爪/超时 15 秒/急停时结束并记录原因；首版无合格抬升证据的尝试保留但不自动当作奖励 0。录像持续包含交还后的运输和放置，便于全局评估。

## 4. 请求/队列接入

在原 `{type:"infer", obs, rtc}` 包外层新增 `pld`（不用已经退役的 `parts`）：

```json
{
  "schema": "pld_sac_block_v1", "mode": "collect",
  "contract_sha256": "服务端握手值", "snapshot_sha256": "服务端握手值",
  "run_id": "批次", "episode_id": "整轮", "attempt_id": "本次抓取", "decision_id": "唯一请求",
  "arm": "left", "elapsed_seconds": 0.0,
  "previous_command": ["14个实际上一tick下发值；不能填测量state代替"]
}
```

`obs`/`rtc`仍按原完整协议。服务端 `actions` 仍为 50×14 物理目标，新增 `pld` trace 包含原 Pi base、可行 scale、采样 u、实际 offset、输入 x、起止 tick 和身份。

每个决策实际负责 `[start_tick, end_tick)`；包括 d 个已承诺 tick＋8 个新动作 tick。只执行这部分并生成一次回执，下一请求的观测 tick 必须等于这个 end_tick。返回的其余 Pi 后缀用于下一段已承诺队列，不得被旧决策重复认领。只有收到且未过期的完整响应才可选择；超时/被替换响应/丢帧/取消时按现有控制安全逻辑回退，明确 `status`。不为凑齐训练数据暂停控制或假造连续 tick。

响应内已有前缀与历史动作来源必须复用，不能因为数组出现在新响应里就重写来源。服务端保证前缀不变，客户端验收也需做逐值检查。当前单活动专家块安排属于新实验调度，不要求改掉原 RTC 模式；通过实验开关关闭时恢复旧路径。

## 5. 最少新增记录

复用原 HDF5 大数组存储；导出时组装为每 decision 一条 JSONL：`{proposal: 服务端完整pld响应, receipt: 实际回执}`。不要只保存最终偏移向量，原 Pi base 与最终提交值都要留。每个 receipt 字段：

| 字段 | 含义 |
|---|---|
| decision_id / epoch / start_tick / end_tick | 精确关联请求与执行区间 |
| status | executed / canceled / partial / rejected 等 |
| ticks | 连续实际控制 tick，长度 d+8 |
| monotonic_times | **float64**，长度 d+8+1，各动作开始及最终结束时刻 |
| submitted_actions | 实际提交的 `(d+8)×14` 目标 |
| client_modified / human_intervention | 布尔，额外限幅/映射或接管必须标记 |
| observation_ref / next_observation_ref | 原始 episode/segment/row 及三路帧索引的稳定引用；下一条起点必须等于这一条终点引用 |

原 recorder 继续存三视频、相机时间/FPS/帧索引、state、FK与闭爪参考、控制来源。模型输入 x 一并保存便于精确重放；原 RGB 不可因此省略。episode manifest 增加 base/actor/contract/recorder代码版本和实验组。失败/取消数据同样归档，不删。

奖励独立 sidecar，每 attempt 一条：

```json
{
  "run_id": "批次", "episode_id": "整轮", "attempt_id": "抓取",
  "final_decision_id": "该抓取最后完整动作块", "outcome_tick": 12345,
  "status": "held", "lift_m": 0.07, "view_valid": true, "held_after_lift": true,
  "reviewer": "分类器版本+人工审核批次", "evidence": ["录像与帧引用"], "split": "train"
}
```

`held→1`，`empty→0`；中间块0。缺证据 `unscored` 保留待处理，不伪装失败。终点按已执行块的 tick 关联，人工晚看/晚审核无影响。整轮另外记录开始待分数量、结束新增正确分好数、分错/掉落数、结束原因，`C/N` 暂作整体效果评估，不摊到每帧。

## 6. 第一批具体采法

1. **先 2 轮 probe 联调**：不施加修正，验证三视频、完整动作块、时间与 request→执行→奖励能够一致回放；左右臂都覆盖。再跑 shadow 检查新增延迟与取消率。这里只验收链路，不宣布模型变好。
2. **首包 collect：先 2 轮试采，核对后再采到约 10 轮**。初始 actor 均值为0、std=0.2。不用刻意救每次空抓；保留正常成功、空抓与失败。只有实际危险时用已有急停。尽量保持与 probe 相同的积木数量/摆放难度/光照，并记录中途变化。
3. 服务端先自动判录像并抽检新增分布（尤其假成功），产出1/0奖励。目标至少60次合法带修正尝试，双臂各20以上并包含两种结果；10轮不够按**有效尝试数**补采，不机械凑集数。两轮 probe 作为同合同基线 replay；collect 最后一整轮预留开发验证，其余训练。验证集可以有少量事件，不能宣称统计显著。
4. 第一轮 SAC 更新后导出新包，不在初始数据上反复多训到“看上去 loss 好看”。用新包 **probe/eval 交替各4轮**，固定布置规则，eval 关闭噪声，避免训练组与评估组混用。每组4轮仅为小规模方向检查，后续论文评估需扩充。
5. 若无危险/边界/延迟问题，再收下一批 collect，回填奖励、累计 replay、从上一 learner 连同 optimizer 继续。奖励审核版本、代码、checkpoint、实验结果全部保留。若探索近乎全零先检查可行scale/限幅和触发，不靠把1000步改成100万步解决。

优先看的真机指标：抓起持住率、空抓率（含左右臂分项）、每次抓取耗时、整轮正确比例、掉落/分错、急停/取消/改写比例、真正执行非零修正的比例。短期抓取提升但分错变多，不能算整个分拣任务改进。
