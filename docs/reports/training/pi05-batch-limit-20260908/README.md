## Batch选择

推荐64（每卡16），不取92作为长训默认：从64到92，吞吐仅增约8.8%，活跃显存从18.54GiB升到
预算上限21.637GiB，缺少额外运行波动余量。32→64的吞吐收益约36%，64是本轮较合理的折中。
这只是硬件/吞吐选择；还没有进行32/64/92的等样本预算、等wall-time收敛与泛化对照。

更大batch降低梯度估计噪声，但不保证更好的泛化或更少训练时间；固定样本数时batch增大意味着
优化器更新次数变少，学习率和训练长度需要一起考虑。相关一般证据见
[An Empirical Model of Large-Batch Training](https://arxiv.org/abs/1812.06162)，不能将其当作Pi0.5最优batch的实测。
第一版不按batch倍率线性放大学习率，沿用原AdamW的2.5e-5峰值作为起点。

## 连续随机取数与保存

`b64-stream` 使用全部train轨迹的真实随机loader，seed42，8个worker，30个不同batch；
真实全参数前向/反向/AdamW更新共30次。首batch创建与首次编译另计。
后29步平均3.3895秒/步，最后12步平均3.3862秒/步；平均数据等待0.0328秒/步。
本轮非保存阶段每卡活跃分配峰值约18.134GiB，反映不同编译/分配布局，不声称与固定batch逐位相同。
它表明当前8-worker供给在这次短测中不是主要瓶颈；NFS负载、数据热缓存和长时间运行仍可能改变吞吐。
保存完成状态和耗时见 `b64-stream/metrics.jsonl` 的 `checkpoint_saved` / `complete`；
checkpoint只用于验证保存流程，不作为正式训练或任务效果候选。真实全尺寸恢复与任务评估不在本次已验证范围。

## 步数依据与时间

metadata：train 4,458轨迹、10,374,181帧、30fps，约96.057小时；val69轨迹、165,142帧。
三相机同时拍摄，不把小时数乘3。相邻帧及50步动作窗口高度相关，原始帧数不是独立场景/技能数量。
大单任务数据提供更多覆盖，但单看小时数不能确定最优步数，也没有必须完整训练一个epoch的规定。

当前随机sampler在一个epoch内按帧无放回取样。以下“覆盖”只指作为当前观测/动作窗口起点的帧占比，
不是动作标签总覆盖，也不是采集了对应时长的新独立轨迹。

| 更新步数 | 起始帧次数（batch64） | 训练帧覆盖比例 | 按3.3895秒/步的循环时间 |
| --- | --- | --- | --- |
| 10000 | 640000 | 6.17% | 9.4小时 |
| 30000 | 1920000 | 18.51% | 28.2小时 |
| 60000 | 3840000 | 37.01% | 56.5小时 |
| 100000 | 6400000 | 61.69% | 94.2小时 |
| 约162097 | 约10374181 | 约1 epoch | 152.6小时，约6.4天 |

这些是短测外推，不含启动、保存、验证与资源波动。排期初步留30k约30–36小时、60k约60–72小时；
1epoch加额外开销可能接近或超过现有7天分配，不作为第一版必达指标。

建议先锁定验证集、样本位置及flow噪声种子：在69条val轨迹各取16个分布于全程的起点，
报告轨迹等权指标，并检查任务阶段覆盖，避免长轨迹或静止片段主导平均值。
数据split来自既有train/val发布，跨采集场次近重复/场景重合尚未作为本轮验收项目。
评估同时看固定噪声验证loss、实际采样的反归一化关节动作误差、夹爪误差，不能只看训练loss。
离线动作指标不替代闭环分拣成功率、误分、掉块和任务耗时；闭环测试需要单独执行。

决策规则：10k先排查明显学习/数据问题；30k评估作为第一版交付候选；若验证仍持续改善，继续至60k。
若连续3次评估已无超出轨迹级波动的改善，或训练改善而验证持续恶化，停止加步数并保留验证最佳checkpoint。
60k仍有明确改善再讨论100k；未观察学习曲线前，不把60k称为已证明足够或最优。
