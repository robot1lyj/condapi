## 3. RTC 的问题到底在哪里

RTC 的观测、计划和执行并不同时发生。新观测到来时，机器人可能还在执行旧请求已承诺的动作。直接把“本次请求返回的整个动作块”视为“下一个观测前全部执行的动作”，会让训练数据的动作与转移不一致。

当前处理分成四件事：

1. **保留前缀。** `wire_plan` 保留原 RTC 前缀值；只在 delay 后的可编辑部分增加残差。
2. **平滑包络。** actor 输出活动臂的一组 7D 修正，8 tick 权重为 `[0,1/3,2/3,1,1,2/3,1/3,0]`。它不是客户端每 8 tick 必须再请求一次。
3. **按真实区间建 replay。** `reconstruct_intervals` 使用相邻原生观测区间，逐 tick 核对来源 token、model_index 与实际 submitted_action，取消、断档、人工控制和未知改写不能被拼过去。
4. **追溯延迟效果。** 某次 actor 修正可能在下一观测区间的 RTC 前缀才执行。`actor_effects_before_handoff` 保留原请求来源，检查交还前确实执行了非零修正，不重命名动作、不搬动 transition 边界。

来源：`block_contract.py::envelope_weights/feasible_scale/decode/wire_plan`、`curator.py::reconstruct_intervals`、`block_replay.py`、`runtime.py`，均固定于本记录 source_commit。

HTML 中 tick 100/104/107/110/112 的时序是为解释机制构造的示例，不是从真实录像抽出的轨迹，也未模拟实际网络耗时。动作来源可被核验，不意味着已经证明某次修正对任务成功的因果贡献。

## 4. 限幅与零修正的定义

首集夹爪 SDK 上限 0.98 导致部分 raw Pi 与实发命令不同。修订后按 manifest 的声明转换核验，116/116 区间均有来源，其中 12 个记录已知端点转换。

正式合同区分：

- `raw_base`：Pi 原始计划。
- `base/actions/wire_actions`：保持客户端校验和 RTC 前缀的网络计划。
- `physical_base/physical_actions`：经过声明 SDK 映射的物理命令，供特征、残差和 replay 使用。

因此“零残差”是等于相同物理映射下的 Pi 基线；不能用 SDK 的裁剪差值冒充学到的动作。未知改写仍拒绝。这项修订解决了已知协议语义不一致，没有证明接触或碰撞安全。

## 5. 介入、抬升与奖励的修订

旧门控存在两个真实反例：稀疏推理观测错过 0.65 张开阈值；宽积木使实际持物开度没有降到 0.62，窗口跨到下一次抓取。新版采用相对收拢、相对重新张开、Pi 未承诺后缀预测，以及当前现场抓取高度范围。

同一集重放由旧 20 个候选修订为 38 个相对收拢候选；在线回放 37 窗口，0 窗口跨两个新版闭合；36 个可唯一关联，1 个左臂窗口因另一臂仲裁晚进入而暂不发奖。35 个候选具备抬升画面，这不是 35 次成功，更不是独立泛化验证。

最新离线抬升资格要求画面位于参考低点之后，避免把接近阶段高处误当作后续抬升。在线“交还”与离线“成功奖励”职责不同：高度是时序/资格线索，持物还要视觉证据。当前每窗口末个核验 transition 只发一次 1/0；整轮 C/N 只评估，不进入本阶段 SAC 更新。

当前奖励只接纳窗口内终态证据，交还后 Pi 才完成的补救不记专家成功。这是首版监督范围；未来若研究下游交接效果，应另定义评价窗口，而不是把所有晚到反馈都删掉。

## 6. 与原研究稿的差别

- 原计划提出 Cal-QL＋SAC；现在的新动作块 SAC 尚未接入同合同 Cal-QL 初始化，不直接迁移旧单 tick critic。
- 当前 Q 的动作输入是带可行比例的 7D 残差参数，状态包含参考计划与队列信息；执行命令通过固定解码与 trace 校验。不能沿用原概念稿文字称它直接输入完整实发动作序列。
- 已做 18 组离线实验及合成 SAC 更新；尚无真实修正的在线学习收益。
- 双臂均可进入，但同一时刻只修正一臂；不是双臂联合残差策略已验收。
- 论文工作只记录这些事实，不发训练命令，不替项目线程改变配方。

## 7. 后续优先补证据

先核验新 collect 的真实非零执行及奖励，再看同合同 SAC 是否稳定更新。随后用 Pi / 确定性专家对照报告空抓、持住、耗时和整轮表现。旧离线 RMSE、服务延迟或合成测试通过，均不替代成功率实验。

当前最值得保存的是失败如何推动合同修订、哪些错误在真实 probe 才出现，以及修订后在新数据中是否仍成立。先积累这些证据，不预设它们一定构成算法创新。
